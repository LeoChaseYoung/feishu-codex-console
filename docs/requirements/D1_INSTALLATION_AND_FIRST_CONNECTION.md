# D1 安装与首次连接 PRD

> 产品：Feishu Codex Console
> 状态：`beta.4` 闭环已完成
> 优先级：P0
> 目标版本：`1.0.0-beta.4`
> 依赖：Node.js 22+、Codex 登录态、用户已有飞书自建应用

## 1. 已确认边界

MVP 绑定用户已有的飞书自建应用，不替用户自动创建飞书应用。

初始化向导负责：

- 检查本机运行环境。
- 引导绑定已有飞书应用。
- 验证 Bot 身份、所需权限和事件能力。
- 自动识别安装者的 `open_id`、测试会话的 `chat_id` 和会话类型。
- 选择默认项目和权限预设。
- 生成私有配置。
- 安装后台服务。
- 发送第一张测试卡和新手引导入口。

初始化向导不负责：

- 替用户注册飞书账号或创建企业。
- 绕过企业管理员审批应用权限。
- 自动发布飞书应用版本。
- 保存 App Secret 到项目仓库或桥接服务 `.env`。
- 为用户修改 Codex 或操作系统账号安全策略。

## 2. 用户问题

当前能力可以运行，但第一次安装涉及飞书应用、Bot 身份、事件、成员 ID、项目路径、权限模式和后台服务。新用户不知道步骤之间的依赖，也无法判断失败发生在哪一层。

需要把“阅读文档并手工拼装配置”变成一个可暂停、可恢复、可验证的安装流程。

## 3. 目标

### 业务目标

- 新用户在 10 分钟内从运行安装命令到收到第一张飞书测试卡。
- 降低因权限、事件订阅、身份 ID 和配置文件错误造成的安装失败。
- 让个人模式和团队模式使用同一套向导。

### 用户目标

- 明确知道当前处于哪一步。
- 每一步只填写当前需要的信息。
- 失败时知道原因、修复动作和如何继续。
- 不需要理解全部环境变量。

### 安全目标

- 默认使用个人安全或团队安全预设。
- 高级模式需要单独确认。
- 不在命令参数、日志和 Git 仓库中暴露 Secret。
- 配置文件为 `0600`，数据目录为 `0700`。

## 4. 非目标

- 支持 Windows 后台服务。
- 自动申请企业管理员权限。
- 默认启用网络、Web 搜索或完全访问。
- 在安装阶段配置所有高级参数。
- 为多个 IM 平台提供统一安装器。

## 5. 用户故事

### 个人开发者

> 作为个人开发者，我希望只提供已有飞书应用和默认项目，就能在飞书收到测试卡并开始使用。

### 团队维护者

> 作为团队维护者，我希望在安装时明确区分管理员、操作者和只读成员，并确保普通成员不能获得完全访问。

### 已有用户

> 作为已经通过源码运行的用户，我希望重新运行向导时识别现有配置，不覆盖未知配置，也不破坏 SQLite 数据。

### 故障用户

> 作为安装失败的用户，我希望修复某一步后从该步骤继续，而不是重新输入全部内容。

## 6. 端到端安装流程

```text
运行 npx feishu-codex-console init
  ↓
欢迎页与已有安装检测
  ↓
本机环境检查
  ↓
绑定并验证已有飞书应用
  ↓
验证权限、事件和 CardKit
  ↓
发送测试消息，自动识别用户与会话
  ↓
选择个人安全 / 团队安全 / 高级模式
  ↓
选择默认项目与扫描根目录
  ↓
查看安装摘要并确认
  ↓
备份旧配置并原子写入新配置
  ↓
运行 doctor
  ↓
安装后台服务并等待健康
  ↓
向测试会话发送成功卡
  ↓
进入飞书新手引导
```

## 7. 分步需求

### Step 0：欢迎与安装状态

展示：

- 产品一句话说明。
- 预计耗时。
- 本次会修改的位置。
- 是否检测到已有配置、服务和数据。

行为：

- 新安装进入完整流程。
- 未完成安装从最后成功步骤继续。
- 已安装用户进入“检查、修改配置、修复、重新安装服务”菜单。

### Step 1：本机环境检查

检查：

- Node.js 版本。
- 当前操作系统和后台服务支持情况。
- Codex CLI 是否可执行。
- `codex login status` 是否成功。
- 安装目录、配置目录和数据目录是否安全可写。
- Git 是否可用。

结果等级：

- 通过：继续。
- 提醒：不影响核心流程，可继续。
- 阻塞：给出修复命令，修复后重新检查。

### Step 2：绑定飞书应用

如果 Bot 身份已配置：

- 展示已绑定应用的脱敏信息。
- 允许继续使用或重新绑定。

如果尚未配置：

- 解释需要已有自建应用。
- 提供“启动 lark-cli 配置流程”。
- 用户确认后运行 `lark-cli config init`。
- Secret 通过安全输入或 stdin 交给 lark-cli，不回显、不写入桥接配置。

### Step 3：验证飞书能力

必须验证：

- Bot 身份 Token 可用。
- 能消费 `im.message.receive_v1`。
- 能接收 `card.action.trigger`。
- 具备消息回复能力。
- 具备 `cardkit:card:write`。
- 应用事件接收方式支持长连接。

验证结果必须指出：

- 缺少的具体权限或事件。
- 应在飞书开发者后台的哪个位置修复。
- 修改后是否需要重新发布应用版本。
- “重新检查”入口。

### Step 4：自动识别安装者

流程：

1. 启动最多接收一个事件、最多等待两分钟的只读监听。
2. 提示用户在飞书中给机器人发送任意测试消息。
3. 提取 `sender_id`、`chat_id` 和 `chat_type`。
4. 不保存测试消息正文。
5. 展示脱敏后的识别结果并要求用户确认。

规则：

- 私聊用于确认安装者身份，不加入群白名单。
- 群聊用于确认身份，并默认建议把该群加入白名单。
- 自动识别超时后允许重新监听或手工输入。
- 团队模式仍必须显式确认管理员。

### Step 5：权限预设

默认顺序：

1. 个人安全（推荐）。
2. 团队安全。
3. 高级模式。

每个预设展示：

- 谁可以使用。
- 可以修改什么。
- 是否允许网络。
- 是否允许群聊。
- 哪些动作仍需要审批。

高级模式必须输入确认文字或完成单独确认步骤，不能通过默认回车启用。

### Step 6：项目配置

必填：

- 默认项目目录。

可选：

- 同步 Codex 桌面端保存项目。
- 增加一个或多个扫描根目录。

验证：

- 路径存在并解析真实路径。
- 默认情况下要求 Git 仓库。
- 扫描根目录不能是文件或不安全符号链接。
- 展示预计发现的项目数量和前几个项目。

### Step 7：安装摘要

确认前展示：

- 实例名称。
- 飞书安装者和测试会话。
- 权限预设。
- 默认项目和扫描根目录。
- 配置文件和数据目录。
- 将安装的后台服务名称。

不展示：

- App Secret。
- 完整 Token。
- 测试消息正文。

### Step 8：安全写入配置

要求：

- 新配置写入临时文件后原子替换。
- 配置文件权限固定为 `0600`。
- 数据目录权限固定为 `0700`。
- 已有配置先备份，并记录备份路径。
- 只管理已知键，保留未知高级配置。
- 任一步失败时不留下半写入配置。

### Step 9：自检与服务安装

顺序：

1. 运行完整 `doctor`。
2. 有失败项时停止，不安装服务。
3. 全部阻塞项通过后安装 LaunchAgent 或 systemd user service。
4. 等待进程启动和连接健康。
5. 检查服务使用的是刚生成的配置文件。

### Step 10：发送测试卡

向刚才识别的会话发送一张安装成功卡：

- 设备名称和在线状态。
- 默认项目。
- 当前权限预设。
- “开始新手引导”。
- “打开控制台”。
- “查看安装诊断”。

测试卡发送成功，才将安装状态标记为完成。

## 8. 安装状态模型

```text
not_started
  → environment_ready
  → feishu_bound
  → capabilities_verified
  → identity_discovered
  → preferences_confirmed
  → config_written
  → service_running
  → test_card_delivered
  → completed
```

每一步保存：

- 状态名称。
- 完成时间。
- 非敏感输入摘要。
- 最近错误类型。
- 是否可以安全重试。

不保存 App Secret、Token 和测试消息正文。

## 9. 异常与恢复

| 异常 | 用户看到的结果 | 可执行动作 |
|---|---|---|
| Node 版本过低 | 当前版本和最低要求 | 打开升级说明、重新检查 |
| Codex 未登录 | 登录状态失败 | 运行登录、重新检查 |
| 飞书 Bot 无效 | 当前应用身份不可用 | 重新绑定应用 |
| 权限缺失 | 缺少的权限名称 | 打开配置说明、重新检查 |
| 事件未启用 | 缺少的事件名称 | 打开事件订阅说明、重新检查 |
| 身份监听超时 | 未收到测试消息 | 重新监听、手工输入 |
| 项目路径无效 | 具体路径和原因 | 重新选择 |
| 配置已存在 | 检测到现有安装 | 检查、备份后更新、退出 |
| doctor 失败 | 失败项与原因 | 修复、重新检查 |
| 服务启动失败 | 服务名和日志位置 | 查看日志、重新安装 |
| 测试卡失败 | 服务已启动但飞书发送失败 | 重试发送、运行诊断 |

## 11. 验收标准

### 新安装

- 给定已正确配置的飞书应用和已登录 Codex，新用户可以在 10 分钟内收到测试卡。
- 用户无需手工编辑 `.env`。
- 安装结果可以通过 `doctor` 和 `status` 再次验证。

### 默认安全

- 默认权限是 `workspace-write`。
- 网络和 Web 搜索默认关闭。
- 高级模式不能被误触启用。
- App Secret 不进入桥接配置、日志或进程参数。

### 可恢复

- 身份监听超时后可以重试，而不丢失之前步骤。
- doctor 失败时不安装或启动后台服务。
- 已有配置更新前自动备份，未知配置保留。
- 安装进程被中断后可以从最后安全步骤恢复。

### 多平台

- macOS 使用 LaunchAgent。
- Linux 使用 systemd user service。
- 不支持的平台在写配置前明确阻塞。

### 自动化

- 单元测试覆盖配置生成、身份事件解析和状态迁移。
- tarball 测试从真实 npm 包完成非交互初始化。
- CI 验证安装脚本、包文件和权限模式。

## 14. 仍需产品确认

### 决策 A：安装交互形式（已确认）

推荐：`beta.4` 保持 CLI 向导，不同时建设本地网页安装器。

理由：

- 当前用户是开发者和团队维护者。
- CLI 更容易跨 macOS/Linux、测试和发布。
- 本地网页仍要处理进程、权限、Secret 和服务安装，复杂度较高。
- 等安装流程稳定后，可以让网页调用同一套安装状态机。

### 决策 B：测试卡发送（已确认）

确认：私聊自动发送；群聊在安装摘要中再次确认。提供 `--no-test-card` 关闭自动发送。

### 决策 C：已有配置更新（已确认）

确认：默认备份后合并已知键，保留未知键；只有 `--force-reset` 才完整重建。

### 决策 D：安装完成标准（已确认）

确认：后台服务健康且测试卡发送成功才算完成。使用 `--no-test-card` 时，以服务健康和完整 doctor 通过作为完成标准；仅写入配置不算安装成功。

## 15. 决策记录

### 决策记录 2026-07-16

- 决策：MVP 绑定用户已有的飞书自建应用，不自动创建应用。
- 原因：自动创建会引入企业管理员权限、租户差异和外部账号状态，扩大首版边界。
- MVP 包含：应用绑定、身份验证、能力检查、测试消息、服务安装和测试卡。
- MVP 不包含：创建企业、创建应用、管理员审批和自动发布飞书应用版本。
- 验收标准：给定已有应用，新用户可以在 10 分钟内收到测试卡。
- 后续版本：评估本地网页安装器和更深的开放平台自动化。

### 决策记录 2026-07-16 · D1-A

- 决策：`beta.4` 只提供 CLI 安装向导，不同时建设本地网页安装器。
- 原因：目标用户是开发者和团队维护者；CLI 更容易跨 macOS/Linux、自动测试和发布。
- MVP 包含：交互式 CLI、非交互参数、可恢复安装状态和结构化错误。
- MVP 不包含：本地 Web 服务、浏览器安装页面和两套交互层。
- 验收标准：CLI 覆盖新安装、继续安装、检查、修复和重新安装服务。
- 后续版本：安装状态机稳定后，网页安装器可以复用同一套底层能力。

### 决策记录 2026-07-16 · D1-B/C/D

- 测试卡：私聊自动发送，群聊再次确认；支持 `--no-test-card`。
- 配置更新：默认备份、合并已知键并保留未知键；`--force-reset` 才完整重建。
- 完成标准：doctor 通过、服务健康并成功发送测试卡；禁用测试卡时以服务健康为准。
- 原因：安装完成必须证明真实端到端链路可用，同时避免覆盖维护者的高级配置或在群聊中意外发消息。
- MVP 不包含：自动向未参与身份发现的聊天发送消息。
