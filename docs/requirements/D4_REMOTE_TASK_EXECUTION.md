# D4：远程任务执行

状态：`beta.4` 闭环已完成
优先级：P0
日期：2026-07-16

> 2026-07-17 更新：Task 继续作为可靠执行记录，但不再是所有交互的主要界面。问答与只读分析使用一条可更新的普通 Markdown 回复；任务卡保留给文件/代码执行、控制、审批和异常。完整迁移规则见 [V4 工作区会话交互模型](../V4_WORKSPACE_SESSION_FLOW.md)。

## 1. 产品目标

用户只通过飞书，也能稳定完成任务发起、实时跟踪、补充要求、显式排队、精确停止、失败恢复和结果审阅；任何时刻都能知道任务在哪个项目、模型、权限和 Codex 会话中运行。

## 2. 已确认决策

- 当前会话有任务运行时，普通消息默认追加到当前 Codex turn；发送 `排队 <任务>` 才创建独立任务。
- 同一飞书会话同时只运行一个任务；不同会话可以并发，但同一本地项目串行执行，避免并发写同一工作区。
- 全局并发和每会话排队上限由部署者配置，不提供无限并发。
- 任务状态只有：排队中、运行中、已完成、失败、已停止和已中断。
- 服务重启后，尚未开始的排队任务自动恢复；已经运行的任务标记为已中断，不自动重放，避免重复命令和重复文件修改。
- Codex thread ID 在 thread 启动时立即保存；失败、停止或中断后仍可保留上下文。
- 停止任务不会撤销已经写入磁盘的修改，卡片必须明确说明并保留文件变更入口。
- 超时属于失败，不属于用户取消；失败提示需要给出可执行的下一步。
- 成员任务中心展示本人全部授权项目的任务；管理员在当前项目查看团队任务。每个运行或排队任务都可以单独停止。
- 只读成员可查看任务状态，但不显示停止、重试或重置会话等虚假动作。

## 3. 状态机

```text
创建任务
  → queued
  → running
      → succeeded
      → failed（超时、权限、连接、策略或执行错误）
      → cancelled（用户明确停止）
      → interrupted（服务在运行期间停止）

queued
  → cancelled（用户停止）
  → queued（服务重启后安全恢复）
```

终态不会自动重新进入队列。用户点击“重新执行”时创建新的任务 ID，并通过确认弹窗提醒可能重复修改。

## 4. 核心流程

### 发起与追加

1. 收到消息后先做身份、聊天、项目和外部动作门禁。
2. 没有活动 turn 时创建持久任务、任务卡和队列记录。
3. 已有活动 turn 时把普通消息通过 `turn/steer` 加入当前任务，并回写追加次数。
4. `排队` 明确创建独立任务，卡片展示实时队列位置。

### 运行与审阅

1. 卡片展示项目、权限、模型、推理、会话、耗时或队列位置。
2. Codex 事件归并为最近执行步骤、回复流和文件变更。
3. 停止时中断当前 turn，关闭未完成审批/问题，但不回滚文件。
4. 完成后展示最终回复、token 用量、文件变更、重试和新会话入口。

### 故障与重启

1. thread 一创建就保存原生 ID 和成员访问记录。
2. 排队任务在 SQLite 中保持 `queued`，服务恢复后重新排队。
3. 运行任务在服务停止时变成 `interrupted`，不会静默重放。
4. 错误被分类为超时、安全策略、权限、连接、队列或未知错误，并展示对应恢复动作。

## 5. 验收标准

- 重复飞书事件不会创建重复任务。
- 同一项目不会有两个 Codex 任务同时写入。
- 排队任务前序完成或取消后，剩余卡片的队列位置会更新。
- 普通补充消息成功加入 turn 后，任务卡展示累计追加数量。
- 每张任务卡明确展示项目、模型、推理、会话、权限和耗时/队列。
- 用户可以从原任务卡或任务中心在两次操作内停止本人任一任务。
- 只读成员看不到会失败的执行按钮。
- 停止、中断和失败卡都说明已写入修改不会自动撤销。
- 服务重启不会自动重放已经开始的任务；排队任务仍会恢复。
- 超时、安全门禁、权限和连接错误有不同的下一步说明。
