# 全项目正向使用 SOP

这份 SOP 定义 Feishu Codex Console 从部署、首次成功、日常任务、团队协作到升级卸载的完整正常流程。它既是用户操作手册，也是产品验收的正向基线。总入口见 [SOP 总览](SOP_INDEX.md)，异常处理见 [全项目逆向与恢复 SOP](FAILURE_RECOVERY_SOP.md)。

## 0. 使用前先记住

### 产品对象

| 对象 | 作用 | 关键规则 |
|---|---|---|
| 设备 | 运行 Bridge 和本地 Codex 的电脑 | 当前版本一个实例代表一台设备 |
| 项目 | 被授权的本地目录或 Git 仓库 | 项目名必须和路径一起辨认 |
| 项目群 | 团队围绕一个项目工作的飞书群 | 一个项目群永久绑定一个项目 |
| 工作话题 | 群内一条顶层消息及其回复串 | 一个话题对应一段独立 Codex 会话 |
| Codex thread | Codex 原生上下文 | 回复继续；新话题不继承旧 thread |
| 任务 | 一次问答、分析、写文件或改代码 | 按意图采用最小权限 |
| 控制者 | 当前可以停止、审阅或处理交互的人 | 不改变原始发起人和执行权限快照 |

### 三条日常口诀

1. 新事情发新消息，同一件事在回复里继续。
2. 一个项目一个群，项目群绑定后不切换。
3. 先说目标，不用先学命令；命令只用于打开控制面和明确排队、停止。

## P01：准备环境与飞书应用

**执行者：** 部署者或团队管理员。

### 前置条件

- macOS，或支持 systemd user service 的 Linux。
- Node.js 22 或更高版本。
- 本机已安装 Codex 并完成 `codex login`。
- 飞书自建应用已启用机器人、长连接事件和 CardKit。
- 至少一个部署者确实有权访问的本地项目。

### 飞书能力

部署者无需手工查找权限。绑定应用后先运行：

```bash
npx feishu-codex-console@next configure-feishu
```

官方页面会展示本产品需要的最小权限差异；确认前不修改应用，也不会申请通讯录、日历或云文档等无关能力。下面的 scope 清单只用于审查和排障。

核心能力：

- `im:message:readonly`
- `cardkit:card:write`
- `im.message.receive_v1`
- `card.action.trigger`

项目群自动化增强能力：

- `im:chat:create`
- `im:chat.members:write_only`
- `im:message.pins:write_only`
- `im:message.group_msg` 或 `im:message.group_msg:readonly`

### 完成标准

- 飞书应用版本已发布，不只是保存草稿。
- Bot 身份可用，消息和卡片事件均可消费。
- 没有把 App Secret、Token 或真实成员 ID 提交到 Git。

**失败转入：** N01～N05。

## P02：安装并完成第一次真实成功

**执行者：** 部署者；首次个人安装建议使用 `personal` 预设。

### 操作

```bash
npx lark-cli config init --new
npx feishu-codex-console@next configure-feishu
npx feishu-codex-console@next init
npx feishu-codex-console@next doctor
```

按向导在飞书私聊机器人发送测试消息。安装结束后，在飞书发送：

```text
新手引导
```

点击“了解当前项目（只读）”，让系统完成一次真实的只读任务。

### 正常结果

- 安装器写入用户级私有配置和数据目录，不要求编辑仓库内 `.env`。
- 后台服务 PID、实例、配置路径和两个事件消费者都通过健康检查。
- 私聊收到安装成功或欢迎卡。
- 第一次任务强制只读，不修改文件、不消费完全访问租约。
- 首次成功只在真实任务完成后记录，不因卡片被打开而提前完成。

### 验收证据

```bash
npx feishu-codex-console@next status
npx feishu-codex-console@next doctor
```

两条命令无失败项，飞书中的项目和权限与本机事实一致。

**失败转入：** N01～N05、N30～N34、N55～N58。

## P03：每天进入产品并确认设备可用

**执行者：** 所有成员。

### 操作

在机器人私聊发送：

```text
状态
```

需要更多诊断时发送：

```text
控制台
```

### 正常结果

首页只展示当前设备、项目、会话、权限、任务和下一步；控制台再展开飞书连接、Codex 引擎、队列、电源、远程就绪和采样时间。

开始任务前至少确认：

- 设备在线，消息与卡片消费者 ready；
- Codex 可用；
- 当前项目正确；
- 当前成员对项目有权限；
- sandbox 满足本次意图；
- 没有必须先处理的运行中任务或排队冲突。

**失败转入：** N30～N34、N47～N54、N87～N91。

## P04：选择、识别和查看项目

**执行者：** 管理员或有项目 ACL 的操作者。

### 私聊选择项目

发送 `项目`，按名称和路径选择。若当前会话存在运行任务、队列或已保存上下文，确认切换影响后再执行。

### 零 Token 查看项目

发送：

```text
读取项目
```

系统用本地 Git、README、package 文件、语言和目录信息生成有界快照，不调用模型，不运行测试，也不修改文件。

### 正常结果

- 同名项目始终显示可辨识路径。
- 无权项目不出现在列表、搜索和历史中。
- 私聊切换项目会按规则解绑当前 thread，并撤销与旧项目绑定的临时权限租约。
- 项目群内没有切换入口；群的项目来自不可变绑定。

**失败转入：** N35～N40。

## P05：新建、继续和接力会话

**执行者：** 所有可执行任务的成员。

### 私聊

- 直接回复：继续当前会话。
- 发送 `会话`：恢复本人在当前项目的历史 Codex thread、压缩上下文或创建新会话。
- 点击“新会话”：开始新的 Codex 上下文，不删除旧历史。

### 项目群

- 新的顶层消息：新工作话题和新 Codex thread。
- 在机器人回复串中继续：恢复该工作话题的同一 thread。
- 不要在一个回复串中混入另一个项目或无关目标。

### 与本机 Codex 的关系

Bridge 控制的是本机 Codex 原生 thread，但飞书消息、卡片、队列和团队控制记录保存在 Bridge 的 SQLite 中，不会自动镜像成当前已打开的 Codex 桌面对话。需要在本机接力时，应显式恢复对应原生 thread，并先核对项目和最近任务摘要；不要假设桌面端当前窗口已经实时显示全部飞书交互。

### 正常结果

- 恢复会话后项目、模型和可兼容的上下文保持一致。
- 新话题只继承项目和偏好，不继承旧 thread 或临时完全访问租约。
- 压缩只影响上下文体积，不改变项目、任务所有者或权限边界。

**失败转入：** N22、N41～N46。

## P06：自然发起四类任务

**执行者：** 管理员或操作者；只读成员不能创建执行任务。

用户直接描述目标，不必选择任务类型。Bridge 在本地分类，但原始提示词不被重写。

| 类型 | 示例 | 默认权限 | 正常结果 |
|---|---|---|---|
| 问答 | “这个模块为什么这样设计？” | 只读 | 紧凑自然回答，不出现空审阅页 |
| 分析 | “检查登录流程的风险，不要改文件” | 只读 | 可读取必要内容，不写工作区 |
| 内容/文件 | “在 docs 写一份启动说明” | 工作区写入 | 展示真实文件影响，测试不是默认必需 |
| 代码 | “修复重复提交并补测试” | 工作区写入或经确认的更高权限 | 展示文件变更和真实测试证据 |

### 意图安全规则

- “继续解释”“把第二点展开”只在同一成员、项目、飞书会话和 Codex thread 中继承上下文。
- “不要修改文件”“只分析”“不要执行”优先于句子中出现的写入动词。
- 无法确定意图时回退只读，并让用户补充目标。
- 内容任务不因为“写文件”就被强制伪装成代码审阅；代码任务才默认要求测试证据。

**失败转入：** N22～N25、N47～N50。

## P07：管理运行中任务、追加、排队和停止

**执行者：** 任务当前控制者；管理员可在授权范围内显式接管。

### 运行时交互

- 普通回复：追加到当前正在运行的 turn。
- `追加 <要求>`：显式补充当前任务。
- `排队 <任务>`：创建独立的下一项任务。
- `任务`：查看本人运行中、排队、中断和最近任务。
- `停止`：停止当前任务并清理本会话队列。

### 调度规则

- 同一会话严格串行。
- 同一项目跨会话的写入任务也串行，避免同时修改一个工作区。
- 不同项目在全局并发上限内并行。
- 排队任务真正启动前重新检查角色、项目 ACL、仓库策略和 sandbox 上限。

### 停止语义

停止只终止后续执行，不等于撤销已经写入磁盘的内容。停止后先查看文件影响和 Git 状态，再决定是否发送新的修复任务；产品不提供隐式 `git reset` 或一键丢弃。

**失败转入：** N24～N29、N41～N46。

## P08：设置模型、推理强度、权限和额度

**执行者：** 设置自己的成员；管理员不能替其他成员授予完全访问。

### 操作

- 发送 `模型` 或 `设置`：查看 Codex 原生模型目录、模型支持的推理强度和后续任务 sandbox。
- 发送 `额度`：查看 Codex 原生返回的账户额度窗口、剩余比例和重置时间。
- 需要完全访问时，只选择“下一任务”“30 分钟”或“当前会话”临时租约。

### 正常结果

- 设置只作用下一轮任务，不热切换正在运行的 turn。
- “Codex 默认”保持动态默认，不被写死为当前某个模型。
- 模型移除或推理档位不兼容时安全回退，并明确说明原因。
- 额度只展示 Codex 原生数据；读取失败时显示不可用，不根据累计 token 猜余额。
- 完全访问租约绑定成员、会话、项目和必要的 thread，到期、用完、切项目或撤销后回落到安全默认。
- `.feishu-codex-policy.json` 只能进一步收紧权限，不能扩大主机或角色上限。

**失败转入：** N47～N54。

## P09：处理 Codex 追问、审批和外部动作确认

**执行者：** 任务当前控制者；外部动作仍绑定任务所有者和项目规则。

### 普通结构化问题

在问题卡中选择快捷答案、下拉选项、输入非敏感文字或取消。每个问题只能消费一次，并有明确有效期。

### 敏感问题

如果 Codex 请求密码、Token、验证码、密钥或私钥，飞书卡没有回答入口。取消远程处理，回到可信本机继续。

### 运行时审批

默认主操作为“允许一次”；“本会话允许”需要再次确认。审批卡必须展示项目、影响、目录、有效期和作用范围。

### 外部动作

commit、push、publish、release、deploy 和 PR/MR 即使处于完全访问任务，也进入单独的短期确认。确认前再次检查任务所有者、项目、仓库策略和动作内容。

**失败转入：** N62～N68。

## P10：读取结果、验证文件影响和测试证据

**执行者：** 任务控制者；群内原本可见的摘要可供群成员查看。

### 问答和分析

处理态原消息更新为自然回答，不额外堆叠一张大型成功卡；没有文件变化和测试证据时不显示审阅入口。

### 内容和代码任务

主任务卡原地更新为结果摘要，按需打开完整结果或“查看验证”：

- 文件数量、增删行和归因可信度；
- 任务变更、混合工作区或归因未知；
- 实际执行的测试命令、最后一次退出码和脱敏摘要；
- 未运行测试时明确写“未检测到测试命令”；
- 最终测试失败时使用失败视觉，不把 Codex turn 完成伪装成验证通过。

### 审阅边界

- 真实工作区直接被 Codex 修改，因此没有“应用修改”按钮。
- 产品不提供一键丢弃，防止误删任务前已有修改。
- commit、push 和 PR 不是接受结果按钮，必须另行提出并确认。
- `.env`、私钥、证书和疑似秘密正文不在远端展示。

**失败转入：** N69～N74。

## P11：使用附件

**执行者：** 有任务权限的成员。

### 操作

在任务消息中附带受支持的图片或文本文件，并在文字里说明用途，例如“根据这张错误截图定位问题”或“读取附件中的需求并生成测试点”。

### 正常结果

- Bridge 下载到私有数据目录，按大小、数量、类型和保留期限制处理。
- Codex 只获得当前任务需要的附件引用。
- 卡片和团队面板不泄漏附件正文或本机缓存路径。
- 任务结束和保留期到期后按配置清理缓存，不删除飞书原文件。

**失败转入：** N75～N77。

## P12：把已有飞书群绑定为项目群

**执行者：** 管理员。

### 操作

1. 把机器人加入目标群。
2. 管理员在群里发送 `项目` 或任意一句话。
3. 在绑定卡中选择项目并确认“绑定后不可更改”。

### 正常结果

1. 绑定前任何普通消息都不进入任务队列。
2. 非管理员只看到“请管理员完成首次绑定”。
3. 系统先保存不可变“群 ↔ 项目”绑定，再同步群会话状态。
4. 原绑定卡更新为项目工作台并置顶。
5. 群进入可信列表；卡片和文字命令都不能改绑。

### 验收证据

- SQLite 只有一条对应 `chat_id` 和 `project_path` 的绑定。
- `origin=existing`。
- `workspace_status=succeeded`、`pin_status=succeeded`。
- 重启后绑定仍存在。

**失败转入：** N06～N13、N78～N80。

## P13：从私聊一键创建项目群

**执行者：** 管理员。

### 操作

1. 私聊发送 `状态` 或 `项目`。
2. 确认当前项目。
3. 点击“一键创建项目群”。

### 固定执行顺序

```text
取得项目级 single-flight 锁
  → 使用确定性 UUID 创建或找回群
  → 立即保存不可变绑定
  → 同步群项目与会话偏好
  → 邀请有项目权限的成员
  → 发送项目工作台并保存 message_id
  → 置顶同一条工作台消息
  → 私聊发送群入口
```

### 正常结果

`members_status`、`workspace_status`、`pin_status` 分别持久化。全部成功才显示“已创建并配置完成”。再次点击只补失败步骤，不重复建群或重复发送已成功的工作台。

**失败转入：** N14～N21。

## P14：同时使用多个项目和多个话题

**执行者：** 管理员或操作者。

### 推荐拓扑

```text
项目 A → 项目群 A → 话题 A1 / A2 → 各自 Codex thread
项目 B → 项目群 B → 话题 B1 / B2 → 各自 Codex thread
```

### 正常结果

- 卡片始终显示当前项目和会话，避免只靠聊天列表标题辨认。
- 同一回复串的短回复只继承本串上下文。
- 不同项目不共享当前项目、thread、权限租约或写入锁。
- 同项目的写入任务排队，不同项目可并行。

**失败转入：** N22、N24、N35～N46、N78～N80。

## P15：团队角色、任务交接和运行手册

**执行者：** 团队管理员、操作者和只读成员。

### 角色与 ACL

- 管理员：管理成员、项目 ACL、接管和运维。
- 操作者：在授权项目创建和控制任务。
- 只读成员：查看允许的团队元数据，不能创建执行任务。

### 任务交接

群内当前控制者从任务卡选择有项目 ACL 的管理员或操作者。任务保留不可变发起人，只有 `controllerId` 改变；模型、sandbox、项目和外部动作授权不随交接扩大。发起人可收回，管理员可显式接管，均写入审计。

### 团队面板

发送 `团队`。管理员查看授权团队聚合，普通成员只看自己的发起/控制任务。面板仅展示角色、状态、数量、项目负载和 token 汇总，不展示提示词、结果、Diff、附件、路径或原始 `open_id`。

### 运行手册

管理员在项目根目录评审 `.feishu-codex-runbooks.json`。成员发送 `运行手册` 选择模板；需要参数时使用文档化命令。模板只能保持或降低权限，不能预授权完全访问、提交、推送、部署或 PR。

**失败转入：** N81～N86。

## P16：外出前开启远程就绪

**执行者：** 管理员。

### 操作

1. Mac 接通电源并保持网络可用。
2. 在飞书发送 `控制台`。
3. 显式开启“远程就绪”。
4. 确认控制台显示电源、Bridge、双事件连接和 Codex 均可用。

### 边界

Remote Ready 只防止系统因空闲睡眠，不能远程开机，不能绕过合盖、电源、VPN、公司设备策略或网络故障。离线卡片只反映最后采样时间，不声称云端仍在实时监控。

**失败转入：** N30～N34、N87～N89。

## P17：日常运维、诊断和支持包

**执行者：** 部署者或管理员。

### 周期性检查

```bash
feishu-codex-bridge status
feishu-codex-bridge doctor
feishu-codex-bridge version
```

需要安全修复时：

```bash
feishu-codex-bridge doctor --fix
```

需要提交问题时：

```bash
feishu-codex-bridge support-bundle
```

### 正常结果

- `doctor --fix` 只修复私有目录/文件权限、过期健康标记和日志容量，不修改身份、ACL、sandbox 或用户代码。
- 支持包写入私有目录，内容有界且统一脱敏；分享前仍人工检查。
- 日志、健康文件、SQLite 和备份保持私有权限。

**失败转入：** N87～N91、N99～N103。

## P18：备份、升级、回滚和旧安装迁移

**执行者：** 部署者或管理员。

### 手动备份

```bash
feishu-codex-bridge backup --config /absolute/path/default.env
feishu-codex-bridge backups --config /absolute/path/default.env
```

### 升级

先只读预览：

```bash
npx feishu-codex-console@next upgrade --config /absolute/path/default.env
```

确认没有活动任务后执行：

```bash
npx feishu-codex-console@next upgrade --config /absolute/path/default.env --yes
```

升级流程固定为：拒绝活动任务 → 备份并校验 → 目标包 doctor → 停止旧服务 → 安装新服务 → 校验版本、PID、配置、心跳和双消费者。失败时恢复数据，并在旧包仍可用时恢复旧服务。

### 手动回滚

先停止服务，再使用备份 ID：

```bash
feishu-codex-bridge stop --config /absolute/path/default.env
feishu-codex-bridge rollback --config /absolute/path/default.env --backup <backup-id> --yes
feishu-codex-bridge install --config /absolute/path/default.env
```

### 从旧源码安装迁移

```bash
npx feishu-codex-console@next migrate --from /absolute/path/to/old/feishu-codex-bridge
```

迁移不删除旧 `.env` 和数据；新服务健康通过后再人工归档旧安装。

**失败转入：** N92～N98。

## P19：卸载与数据保留

**执行者：** 部署者或管理员。

### 操作

先确认无活动任务并按需备份，再运行：

```bash
feishu-codex-bridge uninstall
```

### 正常结果

- 后台服务和 Remote Ready 进程停止并移除。
- 用户配置、SQLite、备份和日志默认保留，便于恢复；不会自动删除项目代码。
- 如需彻底删除私有运行数据，先核对实际配置/数据目录、备份和审计要求，再由管理员在系统层面单独处理。

**失败转入：** N99～N103。

## P20：贡献、验证和发布开源版本

**执行者：** 贡献者或维护者。

### 本地门禁

```bash
npm ci
npm run check
npm test
npm run build
npm run test:package
npm run release:check -- v$(node -p "require('./package.json').version")
```

### 发布规则

- tag、`package.json` 和 GitHub Release 版本完全一致。
- Ubuntu、macOS、tarball 和真实飞书端到端均通过。
- npm 使用 GitHub OIDC Trusted Publisher 和 provenance，不保存长期 `NPM_TOKEN`。
- 预发布只验证 `next`，稳定版才验证 `latest`；本机 `npm whoami` 不用于判断 OIDC 发布结果。
- CLI/OTP 认证失败必须执行 [npm 发布与认证运行手册](NPM_RELEASE_AUTH_RUNBOOK.md) 的一次性停止规则，不重复登录、不索要秘密、不发布空版本绕过认证。
- tarball 不包含 `.env`、SQLite、日志、附件、真实 ID 或个人路径。
- 用户可见变化、迁移影响、正向 SOP、逆向 SOP 和验收矩阵同时更新。
- 多 Agent 编排当前不进入主线；只记录在 Roadmap，默认保持关闭。

**失败转入：** N99～N103，并按 [发布检查清单](RELEASE_CHECKLIST.md) 阻断发布。

## 全项目正向完成标准

一次候选发布只有同时满足下面条件，才算正向 SOP 通过：

- P01～P03 使用非开发者账号完成一次全新安装和首次真实任务。
- 问答、只读分析、写文件和代码任务各通过一次。
- 项目、会话、模型、推理、额度、临时权限、追问和审批均按规则工作。

- 已有群绑定和自动建群各通过一次。
- 两个项目、两个话题和两个成员的上下文与权限隔离正确。
- 服务重启、备份、升级预览、升级或回滚演练无重复执行和数据丢失。
- 支持包与发布包无凭据、真实身份或私有路径泄漏。
- 对应的逆向 N 场景和[验收矩阵](ACCEPTANCE_TEST_MATRIX.md)已完成签字。
