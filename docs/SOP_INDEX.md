# Feishu Codex Console 全项目 SOP 总览

这份文档是安装者、日常使用者、团队管理员、测试人员和维护者共同使用的运行入口。它回答三件事：正常情况下应该怎样完成工作，异常时怎样安全恢复，以及怎样证明恢复后没有重复执行或扩大权限。

## 1. 产品边界

Feishu Codex Console 是一个本地优先的 Codex 远程工作会话层：飞书负责输入、控制、通知和协作，本机 Bridge 负责鉴权、项目与会话映射、任务编排和恢复，本机 Codex 负责真正的理解与执行。

它不是通用聊天机器人、云端 IDE、代码托管平台或远程开机工具。设备关机、断网或 Bridge 未运行时，飞书不能替本机接收并执行任务。

## 2. 不可破坏的产品约定

1. 私聊是个人控制面；项目群是团队工作面。
2. 一个项目群永久绑定一个本地项目；需要另一个项目时创建或进入另一个项目群。
3. 群内新的顶层消息开始一件新事情；在机器人回复串中继续说，延续同一个工作话题和 Codex thread。
4. 提问、分析、写文件和改代码使用不同的最小权限；意图不明确或明确否定写入时一律只读。
5. SQLite 是本地恢复来源；飞书卡片是用户界面，不能反过来制造不存在的成功状态。
6. 已启动任务在 Bridge 异常退出后标记中断，不自动重放；从未启动的排队任务必须重新鉴权后才能恢复。
7. 完全访问是临时租约，不是永久默认；提交、推送、发布、部署和 PR/MR 始终单独确认。
8. 密码、Token、验证码、私钥等秘密不能通过飞书回答，也不能写入卡片、日志、诊断包或审计摘要。

## 3. 全生命周期

```text
准备飞书应用和本机环境
  → 安装、发现身份、验证双事件连接
  → 在私聊完成一次真实只读任务
  → 选择项目与会话
  → 提问 / 分析 / 写文件 / 改代码
  → 追加、排队、停止或处理 Codex 追问与审批
  → 查看结果、文件影响和真实测试证据
  → 建立项目群并进行多人协作
  → 日常诊断、备份、升级和回滚
  → 卸载服务或参与开源维护
```

发生异常时统一采用相反方向：

```text
停止扩大影响
  → 记录用户可见现象和任务/会话/项目 ID
  → 读取 SQLite、健康文件和飞书远端的权威事实
  → 只修复最小失败步骤
  → 重新鉴权或重新确认
  → 验证没有重复任务、重复群、重复工作台或权限扩大
  → 留下审计与验收证据
```

## 6. 按角色执行

### 个人使用者

首次按 P01～P03 完成连接；日常主要执行 P04～P11；外出前执行 P16。发生问题先看控制台，再按 N30～N77 处理。

### 团队管理员

除个人流程外，负责 P12～P15、成员角色和项目 ACL，并在 P17～P19 中承担备份、升级和卸载责任。管理员可以接管或撤销，但不能替成员创建完全访问租约，也不能绕过外部动作确认。

### 操作者与只读成员

操作者只在已授权项目内创建或控制任务；只读成员只能查看允许的元数据和群内原本可见的信息。角色变化后的排队任务必须重新鉴权。

### 开源维护者

执行 P17～P20，维护 D1～D10 需求契约、自动测试、真实飞书验收和发布检查。任何 UI 成功与本地/远端事实不一致，均阻断发布。

## 7. 每次操作的完成定义

一条流程只有同时具备以下证据才算完成：

- 用户在飞书看到与事实一致的终态；
- SQLite 中对象状态与卡片一致；
- 飞书远端对象（群、成员、消息、置顶）确实存在；
- 本地文件、Git 和测试状态与结果摘要一致；
- 没有重复事件、重复任务或重复外部动作；
- 操作者、项目 ACL、sandbox 和确认范围均未扩大；
- 必要的日志、审计或备份 ID 已保留，且内容已脱敏。

## 8. 文档维护规则

新增用户能力时必须同时更新：正向 P 流程、至少一个逆向 N 流程、验收矩阵、用户入口文档和 `CHANGELOG.md`。仅增加成功路径而没有故障恢复，或仅增加卡片而没有权威状态，都不算功能完成。
