## 3. 首次验收发现的问题与当前处置

### AR-01：旧式运行配置权限不符合当前安装契约（已关闭）

- **严重度：** P1 / 发布阻断。
- **事实：** 当前实例从仓库根目录 `.env` 启动，文件权限为 `0644`；当前产品契约要求配置为 `0600`。
- **影响：** 同机其他账号可能读取成员 ID、项目路径和运行策略；如果未来误把秘密写入该文件，风险更高。
- **当前处理：** 已把运行配置权限修复为 `0600`，并重新安装守护服务。
- **通过条件：** 配置迁移到用户级私有路径或至少修复为 `0600`，重新安装后 doctor/健康检查通过。

### AR-02：运行服务无法证明实际配置文件（已关闭）

- **严重度：** P1 / 可靠性与可诊断性阻断。
- **事实：** `bridge-health.json` 的 `configFile` 为 `null`，LaunchAgent 也没有 `DOTENV_CONFIG_PATH`；直接运行默认 `doctor` 会检查新的用户级默认路径并失败，只有显式 `--config <仓库 .env>` 才通过。
- **影响：** `status`、升级和维护者无法证明“当前 PID 加载的配置”与操作者指定配置一致；不满足 P02/P17 的配置一致性要求。
- **当前处理：** LaunchAgent 已显式传入 `DOTENV_CONFIG_PATH`，健康文件已记录实际配置绝对路径。
- **通过条件：** 走受控旧安装迁移或重新 `install --config`，健康文件记录绝对配置路径，默认操作能明确命中该实例。

### AR-03：团队三角色真实验收缺少测试成员

- **严重度：** 非缺陷，外部验收前置条件。
- **事实：** 本轮已自动创建一个仅含当前用户的专用项目群，群绑定、固定项目、工作台和置顶均成功；但授权成员仍只有一个，无法证明管理员、操作者、viewer 和交接隔离。
- **通过条件：** 提供至少第二操作者和 viewer，或明确将三角色项保留为发布前人工签字。

### AR-04：明确只读问答仍被归类为代码任务并授予工作区写入（已关闭）

- **严重度：** P1 / 核心安全交互阻断。
- **事实：** 用户明确发送“只读回答……不修改文件，不执行测试或构建”，任务 `a70f6ac1` 仍显示为`代码`、`工作区写入`；同 thread 追问 `6863073d` 也继承了相同模式。两次实际都没有运行命令或修改文件，但安全边界只由提示词约束，没有落实到执行权限。
- **扩展复现：** 对 14 条典型新任务话术做本地路由表验收，`帮我分析这个 bug 的原因，不要改代码`、`继续分析，不要改代码`、`请给出优化建议，不修改代码`以及带“验收测试：”前缀的只读问答均错误落入 `code`。这不是单一文案边界，而是“否定写入词被删除后，剩余句式未命中分析/问答规则便默认可写”的系统性问题。
- **影响：** 卡片与用户意图冲突，用户无法从界面确认只读承诺是否由系统强制；对于完全访问或工作区写入实例，这是信任和误操作风险。
- **通过条件：** 明确只读/问答意图必须落到 `answer` 或等价只读模式，任务卡显示`只读`；沙箱不得授予写权限；“不执行测试”应显示为“按要求未运行”，而不是“未检测到测试命令”。

### AR-05：短问答复用了过重的历史上下文（已关闭）

- **严重度：** P1 / 成本、延迟与移动端体验阻断。
- **事实：** 首条短只读问题累计输入 61,908 tokens，其中本次新增 53,972、缓存 7,936；任务只是询问技术栈。随后同 thread 的一句话压缩追问只新增 1,180、命中缓存 61,184，说明缓存机制有效，但首轮上下文选择过重。
- **影响：** 用户的简单问答会承担与任务复杂度不匹配的上下文读取成本；也会放大飞书端等待时间和额度消耗。
- **通过条件：** 对孤立问答启用轻量路由：优先使用项目摘要/确定性快照，必要时新建轻量 thread；达到阈值时先压缩历史上下文，并在卡片中解释“为什么使用当前上下文”。同类技术栈问答的新增输入应显著低于当前 53,972 tokens。

### AR-06：无上下文“继续”仍启动昂贵的模型任务（已关闭）

- **严重度：** P1 / 成本与交互阻断。
- **事实：** 执行“新会话”后直接发送“继续”，系统虽然最终正确提示“没有可恢复上下文”，但仍创建了任务并调用 Codex：累计输入 60,176 tokens，其中新增约 13,840、缓存 46,336，另有 658 输出，并执行了 1 条只读命令。
- **影响：** 一个可以本地确定的缺参提示产生高成本和等待；移动端用户会误以为系统正在恢复会话。
- **通过条件：** 当 chat/topic 没有当前会话映射时，“继续/接着/刚才那个”等指代消息由 bridge 直接返回澄清卡或可恢复会话列表，模型调用、命令执行和 Token 均为 0。

### AR-07：会话中心预览泄露内部桥接系统提示（已关闭）

- **严重度：** P1 / 产品边界与信息暴露阻断。
- **事实：** “历史会话”卡片的多条预览直接展示英文内部桥接策略文本，例如授权来源与受限工作区规则，而不是用户问题或最终摘要。
- **影响：** 普通用户看到实现细节而不是可识别的会话标题；内部策略文本也不应作为业务内容暴露或参与分享截图。
- **通过条件：** 会话预览仅使用清洗后的用户首问、用户命名或最终摘要；剔除 system/developer/bridge policy 消息，并为既有会话做兼容清洗。

### AR-08：安装契约遗漏“获取群组中所有消息”，项目群普通话题完全不工作（已关闭）

- **严重度：** P0 / 项目群核心路径发布阻断。
- **事实：** 自动创建项目群并显示“直接发起一个新话题即可开始”后，本轮发送了普通只读新话题；飞书只显示用户消息，Bridge 日志没有收到事件，任务数保持 15，审计记录也没有新增。读取当前应用两个已发布版本的权限清单，均具备 `im:message.group_at_msg:readonly`，但均不具备 `im:message.group_msg` 或 `im:message.group_msg:readonly`。[飞书接收消息事件](https://open.larksuite.com/document/server-docs/im-v1/message/events/receive)明确要求后者之一才能收到未 @ 机器人的群消息。
- **产品缺口：** README、QUICKSTART、INSTALLATION 和 `PROJECT_CHAT_SCOPES` 只列建群、加成员、置顶权限，没有把“获取群组中所有消息”列为项目群运行前置条件。当前 `auth scopes` 只返回用户 scope，实机 capability probe 因而给出 `projectChatStatus=unknown`，但整体仍返回 `ok=true`；建群工作流也只验证对象创建步骤，最终错误宣告项目群已就绪。
- **当前处理：** 新增官方 SDK 驱动的一键最小权限流程，安装器会主动提示修复，CLI 支持 `configure-feishu --profile ordinary-group`；产品文案只呈现可执行的一键入口，原始 scope 保留在审计/排障文档。权限确认后已受控重启并完成不 @ 普通消息黑盒复验。
- **通过证据：** 同一已绑定项目群话题发送不 @ 的“状态”，Bridge 收到新的文本事件并返回状态卡；项目群卡片由“修复项目群”转为“打开项目群”。

### AR-09：项目群工作台占据首屏，真正的工作话题被压到折叠线下（已关闭）

- **严重度：** P2 / 移动端与高频使用体验。
- **事实：** 在 1366×768 桌面窗口中，置顶工作台从标题区一直占到接近输入区，首次话题只剩一行可见；卡片同时重复“当前项目”“本群固定连接”“项目已锁定”三段相同语义，并展示与固定群任务无关的全局项目数量、收藏按钮。
- **影响：** 用户进入项目群首先看到的是管理面板而不是正在做的工作；手机端会更明显，违背“打开群就继续任务”的定位。
- **通过条件：** 群内默认只保留一行固定项目状态和“新建话题”主动作，详细分支/策略/项目统计折叠到“详情”；同一屏至少完整展示最近一个话题及其状态。

### AR-10：个人项目群升级为团队群时，新增成员不会被同步（已关闭）

- **严重度：** P1 / 团队生命周期阻断。
- **事实：** 项目群初建时如果 `memberIds=[]`，服务直接把 `membersStatus` 写成 `succeeded`。之后配置中加入新操作者再对同一项目执行 provision，因为状态已成功，`syncMembers()` 被永久跳过。隔离复现：首轮空成员 ready，第二轮增加 1 名成员仍显示 ready，实际同步调用 0 次，期望 1 次。
- **影响：** 个人先试用、之后拉团队是最自然的开源采用路径；界面会声称群已就绪，但新增成员既收不到邀请，也没有待修复提示。角色、ACL 或成员可用范围变化同样没有可靠对账依据。
- **测试缺口：** 当前项目群测试覆盖首次同步、失败重试、并发点击和重启续建，但没有覆盖“目标成员集合在成功后发生变化”。
- **通过条件：** 持久化已同步成员集合或目标集合指纹；每次打开/修复群时计算差集并幂等邀请新增成员，成员移除采用明确策略且不静默扩大权限；加入个人→团队、角色变更和重启后的正逆向测试。

### 初步根因定位

- `inferTaskMode()` 只识别句首问句、分析动词等模式；“验收测试：只读回答……”带业务前缀，去掉否定写入词后仍没有命中问答规则，最终落入默认 `code`。本机用构建产物复现：无上下文和已有代码上下文都返回 `code`；后续“继续……”又继承前一任务的 `code`。
- 当前会话只支持用户主动“压缩会话”，没有根据上下文窗口/新增 Token 阈值自动压缩或为孤立问答启用轻量 thread；因此短问题直接复用已很重的当前 thread。
- 无上下文“继续”进入通用任务路由，而不是先检查 chat/topic 的会话映射，因此把本可确定处理的缺参消息送入模型。
- 会话中心直接取 thread 历史中的前部文本生成预览，没有先按消息角色过滤内部策略内容。
- 项目群能力探针只检查群对象的创建、成员和置顶，不检查群消息事件的实际读取 scope；因此“对象配置成功”被错误等同为“项目群可用”。
